| **REV157-01** HIGH, candidates decided the cash treatment | **One list:** the `unattributed_fee` category is withdrawn. Every open obligation is listed in one `pending_fees` list and carried forward through each successor until it is closed. Candidates are information only. **Cash treatment is decided at `--resolve-fee`,** from the actual activity named, its generation membership and the existing ledger entries. Exactly one of four cases applies and is recorded as `cash_treatment`: (1) `origin_booked`: attribution only; (2) `successor_opening`: attribution only, the cash being already in the opening cash; (3) `successor_reclassified`: booked as the successor's own fee, so no new cash entry, and from then on it is excluded from the successor's P&L; (4) `successor_bridged`: not booked, so one `broker:predecessor_cash` entry. **Account-wide check:** one cash entry and one P&L owner per fee activity (`fee_cash_not_exactly_once`). **Membership:** §7.6.1 is corrected, because today's classifier can give an unlinked late fee `in_generation` of the successor, not only `unresolved_generation_membership`. **Test:** your two-generation case. Two $3.54 obligations, A1 in G1 and A2 in G2, run in three membership variants. Each checks exactly-once cash, the P&L totals, the cash invariants before and after, and that A1 cannot be reused. | spec §4.5.1, §5.1 item 7, §7.1, §7.6.1, §10, §11 |
| **REV157-02** HIGH, two deadline reads | **One decision time:** `at` is sampled once, right after `BEGIN IMMEDIATE`, and used for the run-state refusal, the deadline test and the transition. `entry_refusals` takes `at` and never reads a clock. **The transition forces the refusal:** whenever this transaction records `WIND_DOWN_REQUESTED`, the current intent is refused, so it can never be written `SUBMITTED`. **The test checks where the read happens:** each call of the test clock tries `BEGIN IMMEDIATE` on a second connection with `timeout=0`, and must find the database locked. It also asserts one call per dispatch. The same check applies to the fenced `RISK_APPROVED` write. | spec §8 step 1; Plan A Tasks 3–4 |
| **REV157-03** MEDIUM, weekend coverage | The broker calendar request starts at the last library session on or before the planned end's date, not at `ny_date(now)`. Both ends are session dates, so `compare()` covers every date between them. **Tests:** freeze with `now` on a Sunday (end Monday) and on Thanksgiving (end Friday's early-close day). | spec §4.5; Plan A Task 2 |
| **REV157-04** MEDIUM, startup order | **The order:** `enter_durable_state` is the first database write of startup, before reconciliation or any broker call. It preserves `WINDING_DOWN`, records `WIND_DOWN_REQUESTED` when past the deadline or after `end-run`, or records `run_paused` (`startup_recovery`). **Then** reconciliation runs, the phase is decided, the checks run, and `run_resumed` is recorded on success. **Tests:** reconciliation raising leaves `PAUSED` (and, past the deadline, `WINDING_DOWN`), both read from a fresh connection, with the call order recorded. | spec §6.2; Plan A Task 6 |
