# Rev.147 rev. 10 — response to the rev.158 review

| Finding | Correction | Where |
|---|---|---|
| **REV158-01** HIGH, "exactly one ledger entry" contradicts `successor_opening` | The account-wide check now counts cash **representations**, not ledger entries. Each fee activity has exactly one: **(a)** one ledger movement (`broker:fee:<id>` or `broker:predecessor_cash:<id>`) in the generation whose window contains its posting, and none elsewhere; or **(b)** for an activity posted between generations, no movement anywhere, with evidence that the successor's opening cash includes it (listed `pre_generation` in the opening population, snapshot taken after its posting). Later generations carrying the debit forward in their opening cash is not counted. No ledger debit is ever written to make the count come out. **Test:** variant (c) is now the explicit between-generations case: A2 posts after G1's seal and before G2's opening. It asserts zero movements for A2, that the check passes on opening-cash evidence, and two negatives: an injected `broker:fee:A2` fails, and missing opening evidence fails. | spec §4.5.1, §10 |
| **REV158-02** HIGH, `origin_booked` needs a zero P&L adjustment | Each `fee_attribution` (and `fee_correction`) record carries `fee_amount` and, separately, `pnl_adjustment`. `pnl_adjustment` is 0 for `origin_booked`, because the sealed result already contains the fee. It equals `fee_amount` for the other three treatments. The adjusted result is sealed + Σ `pnl_adjustment`, never + Σ `fee_amount`. Your example is in §7.6.1: A1 (−3.54, adj 0) and A2 (−3.54, adj −3.54) give sealed − $3.54, total fees −$7.08, not −$10.62. **Tests** assert each record's two fields, not only the total, in the two-generation case and in the single-generation `origin_booked` case. | spec §7.6, §7.6.1, §10, §11 |
| **Plan A 1**, calendar test expectations | A Monday 2026-11-16 end now expects `range_start` 2026-11-16. Added: an end on **Sunday** 2026-11-15 23:00 ET (`range_start` Friday 2026-11-13, the original gap), and an end on Thanksgiving 2026-11-26 (`range_start` 2026-11-25). The Friday 2026-11-27 end expects 2026-11-27. The test asserts the start the simulator's `get_calendar` call received. All session dates were checked against XNYS. | Plan A Task 2; spec §10 |
| **Plan A 2**, precondition signature | `connection_precondition: Callable[[sqlite3.Connection, datetime], Sequence[str]]`, with the `clock` argument declared on `update` in the same line. It is required whenever a precondition is passed. | Plan A Task 3 |
| **Plan A 3**, `decide_phase` is pure | `decide_phase(state)` maps `WINDING_DOWN` to `"wind_down"` and `PAUSED` to `"resume_checks"`. It takes no clock or deadline and writes nothing. `enter_durable_state` owns every startup write. `run_resumed` moved to startup step 5. Added `test_decide_phase_is_pure`. | Plan A Task 6 |
