| **REV156-01** HIGH, fee corroboration could imply attribution | **The obligation:** each wind-down crypto sell fill gets one `fee_obligation:<fill_id>`. **What closes it:** only a broker-identity link (never present for crypto, per G1), or an operator `--resolve-fee`, which is validated by amount (`fee_attribution_amount_mismatch`) and unique per activity (`fee_activity_already_attributed`). **An amount match** is recorded as `fee_amount_candidates`, and never consumes an activity, closes an obligation, or makes fee accounting complete. **The cash** of every fee activity is booked once as an `unallocated_account_fee`, separately from attribution. **At the seal:** open obligations are listed as `unattributed_fees` (cash booked in this generation) or `pending_fees` (no cash yet). `fee_accounting` is `complete` only when every obligation is closed. `fee_corroborated` and `fee_amount_unmatched` are withdrawn. **Tests:** two equal expected fees with one activity; an unrelated or predecessor fee of the same amount; repeated reconciliation without reuse. | spec §4.5, new §4.5.1, §5.1 item 7, §7.1, §10, §11 |
| **REV156-02** HIGH, the cutoff depended on the watcher | The dispatch transaction reads the clock **inside** `BEGIN IMMEDIATE` and compares it with the frozen `planned_end_at − lead`. At or past the deadline it refuses the BUY (`RUN_WIND_DOWN_ACTIVE_AT_DISPATCH`) and records `WIND_DOWN_REQUESTED` (cause `deadline_at_dispatch`) in the same transaction, which rejects every other `RISK_APPROVED` BUY. The fenced `RISK_APPROVED` write applies the same test. **Tests:** the watcher never runs, the clock is advanced past the cutoff, and no BUY commits `SUBMITTED`; and a clock read twice proves the read is inside the transaction. | spec §8 step 1; Plan A Tasks 3–4 |
| **REV156-03** MEDIUM, freshness is not agreement | Freeze fetches `get_calendar` read-only, with the broker it already uses, and runs the existing pure `compare()` in memory. Every date from `planned_end_at` through `next_session_open` must be covered and `agreed`. A failed fetch, a `contested` date, or short coverage (a fresh check for other dates) refuses with `wind_down_end_calendar_unverified`. The evidence is frozen in the manifest (`policy.wind_down.calendar_evidence`) and never written to the database, so `_require_fresh` is untouched. `CalendarGate.fresh` is not used. | spec §4.5; Plan A Task 2 |
| **REV156-04** MEDIUM, the pause was not persisted after a crash | Before any asynchronous resume check, a `RUNNING` state (no events, or a latest `run_resumed`) gets a `run_paused` event with cause `startup_recovery`, through the transition write. `WINDING_DOWN` is preserved. `run_resumed` is recorded only after every check passes. **Tests:** a no-event crash followed by a failed check leaves the run durably `PAUSED` (read from a fresh connection) and refuses BUYs; and a stale `RISK_APPROVED` BUY is rejected. | spec §6.2 step 3; Plan A Task 6 |
