# Generation-2 Calibration Data Freeze

## Why this exists

Rev.89's entry-composite calibration ladder concluded with `NEW CALIBRATION GENERATION REQUIRED` (see `docs/entry-composite-calibration-ladder.md`): the corrected TRAIN/VALIDATION/HOLDOUT methodology selected a different frozen candidate than the original run, and the original run's HOLDOUT had already been viewed, so it could not be reused to evaluate the new candidate without contaminating it. The question that followed was whether a genuinely untouched historical window still existed somewhere in the currently-cached Alpaca data that could serve as a valid new holdout, rather than requiring a wait for brand-new market days.

## The lineage audit

A read-only audit of every Rev.86-89 calibration/forensic tool and report, checked directly against source and the actual cached data (not assumed from docstrings), found:

- **The cache's own ceiling**: `tools/historical_data/fetch_alpaca_history.py` requests from 2015-01-01 onward (`FETCH_START`) and records whatever Alpaca actually returns. Confirmed actual coverage: most equities 2020-07-27 -> present (IEX feed reliability floor, confirmed in `docs/exit-intelligence-portfolio-optimization-calibration.md`), SPY 2018-11-01 -> present, crypto 2021-01-01 -> present (Alpaca has no BTC/USD data before that date, confirmed in `docs/regime-classifier-phase1-calibration.md`). This is a data-source ceiling, not an unfetched gap -- there is nothing deeper to go looking for from this source.
- **`calibrate_exit_params.py` (Rev.86)**: its four walk-forward folds compute `train_entries` as *every entry with `entry_date <= fold["train_end"]`* (`tools/historical_data/calibrate_exit_params.py:136`). Fold_1's `train_end = 2022-12-31` alone means the entire pre-2023 cached history was scored as a "train" window and aggregated into `results.json` / `docs/exit-parameter-calibration.md`.
- **`diagnose_signal_sparsity.py` (Rev.86)**: iterates `range(MIN_CANDLES - 1, len(bars))` with no date filter at all -- the entire cached range, every symbol.
- **`entry_composite_audit.py` (Rev.87)**: reuses `diagnose_signal_sparsity.py`'s samples directly ("Phase 2 -- independently reproduces that finding against the same cached data") -- same unrestricted range.
- **Regime-classifier Phase 1 calibration**: individually names, dates, and tabulates specific historical periods spanning the *entire* cached range in `docs/regime-classifier-phase1-calibration.md`, including its earliest dates ("Dec 2018 low -> recovery", "COVID crash 2020-02-19..2020-03-20", "2019 full year (steady bull)").
- **`entry_calibration_ladder.py` (Rev.89)**: TRAIN 2023-01-01 -> 2024-12-31, VALIDATION 2025-01-01 -> 2025-08-31, HOLDOUT 2025-09-01 -> (open-ended, actually ends at cache end). `pool_for_date()` excludes pre-2023 dates from every metric it computes -- but that's the *only* tool with a gap, and every date it excludes was already used or reported by the tools above.

**Conclusion: no date in the currently-available historical range is untouched.** The pre-2023 gap in the entry ladder's own scope is fully covered by Rev.86/87's whole-history tools; the post-2023 range is fully covered by the entry ladder itself. This was proven, not assumed, before deciding to freeze rather than keep searching.

## The freeze

Since no valid historical holdout remains, the only scientifically defensible source of untouched data is **new market days, strictly after a fixed boundary, accumulated going forward and never inspected until Generation-2 opens.**

- **Freeze date: 2026-09-04.**
- **Eligibility rule: a bar is Generation-2-reserve-eligible if and only if its own market date is strictly greater than the freeze date.**
- **The authority is the bar's market date, never a fetch or file timestamp.** Refetching an old bar after the freeze date does not make it eligible -- this matters because `fetch_alpaca_history.py` re-fetches from `FETCH_START = 2015-01-01` every time it runs; without this rule, a routine cache refresh could silently "launder" already-contaminated dates as if they were newly observed.

The manifest recording this is `data/calibration/generation_2_freeze_manifest.json` -- generated by `tools/historical_data/create_generation2_freeze_manifest.py`, which records the freeze date, the eligibility rule, the git commit it was created from, a per-symbol `first_bar_date`/`last_bar_date` snapshot of everything contaminated as of the freeze, and a SHA-256 fingerprint (`integrity_sha256`) computed over the content fields only -- re-running the creator against unchanged underlying data reproduces the identical hash; a changed hash means the recorded facts changed, not merely that time passed.

Unlike everything else under `data/calibration/` (regeneratable cache, gitignored), **this manifest is deliberately git-tracked** (see the `.gitignore` exception) -- it is a scientific commitment, not cache, and its history must be auditable.

## The guard

`tools/historical_data/generation2_freeze.py` is a small shared module any future Generation-2 calibration script must use to classify bars, rather than re-deriving or hardcoding the freeze date itself:

- `freeze_date()` -- reads the boundary from the manifest.
- `is_generation2_reserve_eligible(market_date)` -- true only if strictly after the freeze date.
- `assert_reserve_is_uncontaminated(market_dates)` -- raises `Generation2FreezeError` immediately if any date at or before the freeze boundary has been included in a claimed reserve/holdout set, rather than silently producing a result that looks clean but isn't.

This keeps the boundary enforceable in exactly one place. No tradepulse/ production code was touched -- this is calibration tooling only.

## Rules while the reserve accumulates

1. The reserve may be fetched and cached as new market days occur.
2. It must **not** be loaded into calibration-selection, threshold-search, weight-search, diagnostics, or reports of any kind until the Generation-2 candidate is completely frozen. No peeking, including informal "how's it looking" checks.
3. The manifest itself never decides which model wins -- it only proves what data was eligible before Generation-2 calibration starts.
4. Changing `FREEZE_DATE` in the creator script is itself a scientific decision. It must never be moved to make a later reserve look more convenient; a new freeze requires its own equally-audited justification.

## Proposed opening rule (not yet implemented)

The reserve must not be opened based on "it looks like enough" -- the threshold must be set before anyone looks at reserve-side performance. Proposed (for review, not yet enforced by any code):

- **Minimum elapsed market span**: at least 6 calendar months of new trading days past the freeze date, so the reserve isn't dominated by one short-lived regime.
- **Minimum qualifying sample size**: at least 30 forward-scored opportunities per asset class (equity and crypto counted separately), mirroring the existing `MIN_VALIDATION_EXPECTANCY_TRADES = 30` precedent already used as a promotion floor in `entry_calibration_ladder.py`.
- **Equity coverage**: opportunities present across at least a majority of `DEFAULT_EQUITY_UNIVERSE`'s sectors, not concentrated in one or two names.
- **Crypto coverage**: opportunities present across at least 3 of the 5 default crypto pairs.
- **Regime diversity where objectively measurable**: the reserve window should not register as a single regime label (per the existing regime classifier) for its entire span -- at least two distinct classified regimes should appear, so the same promotion metrics (expectancy, profit factor, drawdown, concentration, stability) aren't being computed over one uniform market condition.

If the reserve does not meet all of these when first checked, the correct response is to keep waiting, not to relax the rule. This section is a proposal for review -- no code currently enforces it, and none will until it's confirmed.
